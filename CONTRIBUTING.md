# Contributing

## Branching & promotion

Promotion flow: **`feature branch → dev → main`**.

- Branch from `dev`; name `<topic>` (or `claude/<topic>` for agent work).
- **Open every PR against `dev`.** `main` is release-only; `dev → main` is the
  release promotion step.
- Releases are auto-tagged. The version is `max(patch-bump, ./VERSION)`. Patch
  releases are automatic — to cut a **minor/major**, bump `VERSION` in the `dev` PR.

## Work loop

1. Pick or open an issue (use the forms in `.github/ISSUE_TEMPLATE/`).
2. Branch from `dev`.
3. Open a PR with **base `dev`**, body containing `Closes #<issue>`.
4. On merge, the issue closes and the release pipeline runs on `dev`.

## Before a PR is ready (and after each conflict resolution)

A clean diff against a *stale* base hides regressions. Before marking ready — and
again after resolving any conflict:

1. **Re-sync with base.** `git fetch origin dev` and rebase.
2. **Check what else touched your files:**
   `git log --oneline <branch-point>..origin/dev -- <file>`. If another PR changed
   it, read the **current `dev` version** of the functions you're editing and
   reconcile *intent* — don't just re-apply your hunks.
3. **Treat the conflict resolution as authored code** — pin each side's intent
   with a test.
4. **Confirm the gates are green** locally and that the PR's required checks
   actually reported (a required check that never ran is not a pass).
5. **Move the docs** (see below).

## Gates

CI runs `cargo fmt --all --check`, `cargo clippy --all-targets --locked -- -D
warnings`, and `cargo test --locked` on every PR that touches the Rust/BPF tree
(docs-only PRs skip them). Run the same three locally before marking ready.
Building needs clang ≥ 16 and `libelf-dev`/`zlib1g-dev` (see README →
Requirements); running the scheduler needs a sched_ext kernel, but the tests
don't.

## Done = docs updated

Every change moves its matching artifact, or explicitly notes N/A — README.md
for user-facing behavior (flags, config keys, service setup), DESIGN.md for
policy/architecture changes. The PR template has a checkbox for this — keep it
honest.

## Project invariants

Two guarantees must survive every change (the PR template asks about both):

- **Fallback safety.** Daemon exit, crash, Ctrl-C, or the sched_ext watchdog
  always detaches the scheduler back to EEVDF. No per-wakeup BPF path may block
  or starve a runnable task.
- **Single source of truth for shared layout.** Every struct/constant shared
  between the BPF program and the daemon is defined once in `scx_cohort_common`;
  `intf.h` is generated by cbindgen and never hand-edited, and the layout tests
  move together with any change.

## Local hooks

Run `./scripts/install-hooks.sh` once to install the fast pre-push hook
(`cargo fmt --all --check`; clippy and tests run in CI).
